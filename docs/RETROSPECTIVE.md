## 一、项目定位（上游项目）

ArkPlots 解决《明日方舟》玩家的一个真实痛点：剧情量庞大（主线、别传、故事集、集成战略等 8 类）、前置关系复杂，玩家缺一个能**按进度推荐「该补什么 / 能接着读什么」**的本地工具。核心差异化不是「列表」，而是**基于前置关系图 × 个人阅读状态的推荐引擎**（急需补充 / 推荐补充 / 推荐继续 / 可以继续 四级）。

**本地二次开发所做的工作**：Android 纯离线版（Capacitor 打包、封面压缩、数据层双端分流、移动端 i18n）+ 2026-10-25 安全加固（详见下文）。本复盘后半部分的架构评价针对上游代码库，加固内容为本地改动。

## 三、值得保留的架构决策

1. **`app_info.py` 作为版本/发布物命名的单一事实源**。打包脚本、运行时 `/api/version`、更新器、前端版本展示全部从它读。代价近乎为零，换来的是「改一处，处处一致」，永远不出现版本号漂移。
2. **后端坚持纯标准库**。本地 HTTP 服务用 `http.server` 而非 Flask/FastAPI，用户免装依赖、PyInstaller 体积可控、冷启动快。代价是自己处理 MIME/线程/CORS 细节——但这些都沉淀成了测试（如 Windows 注册表把 .js 映射成 text/plain 导致白屏的回归测试）。
3. **更新链路三级降级**：GitHub REST API → tags API → releases.atom 公共 feed + expanded_assets 页面抓取。为的是中国大陆无代理用户在 API 限流（403）时仍能检查更新。这是「面向真实用户环境设计」的典型案例。
4. **数据放 EXE 旁、进度永不丢**。`Read_record.json` 只增改不缩小，缺的 id 补「未读」——升级、换机、数据文件更新都不会清空用户进度。这条不变量写进了测试。
5. **一套前端、两个壳**。桌面（pywebview/WebView2）与 Android（Capacitor 纯离线）共用 web/ 代码，`api.ts` 里 `IS_NATIVE_APP` 分流。移动端为体积把 45MB 封面压到 5.5MB 且不动原图备份。

## 五、经验教训

1. **用户数据文件是攻击面也是脆弱面**。`Plotline.json` 会随版本更新，代码必须防御任意形状的数据（本次修的 `date:null` 崩溃就是例证）。教训：所有对外来 JSON 的读取都该有「已实证的坏形状」回归测试。
2. **面向目标用户的网络环境设计**。海外源 + 大陆用户是本项目的长期约束，更新链路的每次改动都要想着「无代理时还能不能用」。
3. **文档也会烂**。`Update.md` 中文段落曾发生乱序损坏且无人发现——因为它是给用户看的、自己不常读。教训：公告类文件值得在发版流程（skill `arkplots-release`）里加一眼校对步骤。
4. **巨函数是债务**。tkinter `gui_main()` 约 1300 行，功能能跑但没人敢动。web 化替代后它成了纯负债，早该在替代完成时移除。
5. **测试是重构的安全网**。本次敢一次性改四个核心文件并新增安全逻辑，靠的是既有 30 个测试兜底 + 新增 36 个针对性测试。
